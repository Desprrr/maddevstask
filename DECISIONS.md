## 2026-09-15 18:13 (+05:00) — Планировщик: политика следующего запуска

Каждый check обслуживается одним `asyncio.Task`, работающим циклом `проба → запись результата → инцидент/алерт → WS-broadcast → sleep(interval) → повтор`. Следующий запуск планируется от **момента завершения предыдущей пробы**, а не по фиксированной сетке времени. Это даёт «проверка не запускается второй раз параллельно самой себе» автоматически (без отдельных локов), даже если проба длилась дольше своего интервала — единственная плата: интервал в этом случае временно «плывёт» (запуск позже расписания), что задокументировано как сознательный трейд-офф простоты против идеальной пунктуальности.

## 2026-09-15 18:22 (+05:00) — Проблема: жёстко закреплённые версии пакетов не собираются на Python 3.14

При первой установке зависимостей backend (`pip install -r requirements.txt`) с точно
зафиксированными версиями (`pydantic==2.10.4`, `asyncpg==0.30.0` и т.д.) сборка падала и на
Windows, и в WSL2 (Ubuntu 26.04, тоже Python 3.14) — для этих старых версий нет готовых wheel
под cp314, pip уходил в сборку из исходников (`pydantic-core` на Rust), а линковка падала
из-за не до конца настроенного MSVC/Rust тулчейна.

Исправление: в `requirements.txt` заменил точные версии на нижние границы (`>=`), чтобы pip
брал актуальные версии с готовыми wheel под используемый интерпретатор. После этого
`pip install` и `pytest` (health-check) прошли без проблем. Для сдающего проект это тоже
безопаснее: любой более новый/другой Python не упрётся в эту же стену.

## 2026-09-15 18:45 (+05:00) — Локальный PostgreSQL для разработки и проблема с SSL через WSL2

На машине нет Docker и нет нативного Postgres под Windows, зато есть WSL2 (Ubuntu 26.04,
passwordless sudo). Поставил PostgreSQL 18 через `apt` внутри WSL2, завёл роль/БД `monitor`.

Проблема: по умолчанию Postgres в WSL слушал только `listen_addresses=localhost` — недоступно
с Windows-стороны. Поправил на `listen_addresses='*'` и добавил в `pg_hba.conf` правило для
подсети WSL NAT (`172.16.0.0/12`, `scram-sha-256`), не открывая `0.0.0.0/0`. После этого
обычное TCP (проверено HTTP-сервером на порт) стало доступно с Windows по `localhost` и по IP
WSL, но именно Postgres-подключение (`asyncpg`) всё равно рвалось на этапе SSL-negotiation
(`connection_lost` при попытке SSL upgrade) — похоже на особенность NAT-трансляции
localhost-forwarding в этой связке WSL2/Windows, ломающую именно SSL-рукопожатие поверх
проброшенного порта.

Исправление: подключаться с явным `ssl=False` (локальный Postgres и так без TLS). В
`app/config.py` добавлен флаг `DATABASE_SSL` (по умолчанию `false`), передаётся в
`create_async_engine(..., connect_args={"ssl": settings.database_ssl})` — для прод/управляемой
БД с TLS переключается через переменную окружения, ничего не захардкожено.

Это же самое окружение (WSL2 Postgres) используется только для локальной разработки/тестов в
этой песочнице; для сдачи проекта основной путь — `docker-compose`, где Postgres поднимается
в контейнере и подобных проблем с NAT/SSL не будет в принципе.

Небольшие уточнения относительно плана, добавленные прямо в схему:

  задания), а не только валидация на уровне API.
- `maintenance_windows` — CHECK-constraint "ровно один из `check_id`/`group_id` заполнен",
  чтобы окно обслуживания не могло повиснуть без привязки или с двойной.
- `check_results` и `incidents` получили составные индексы `(check_id, ...at)` сразу, под
  требование "история за месяц открывается быстро".

Автосгенерированная миграция `initial_schema` проверена вручную (FK/ondelete, constraints,
индексы совпадают с моделями) и прогнана (`alembic upgrade head`) на локальном Postgres из
WSL2 — все 7 таблиц создались корректно.

Отдельно: WSL2-инстанс по умолчанию засыпает между вызовами (нет активного клиента) и
поднимает Postgres заново при следующем обращении — это ломало соединение с Windows-стороны
("Connection refused") просто из-за гонки. Держу фоновый `sleep infinity`-процесс в WSL на
время разработки, чтобы инстанс не завершался между командами. Это чисто dev-окружение этой
сессии и не имеет отношения к тому, как проект будет запускаться у проверяющего.
