## 2026-09-15 18:13 (+05:00) — Планировщик: политика следующего запуска

Каждый check обслуживается одним `asyncio.Task`, работающим циклом `проба → запись результата → инцидент/алерт → WS-broadcast → sleep(interval) → повтор`. Следующий запуск планируется от **момента завершения предыдущей пробы**, а не по фиксированной сетке времени. Это даёт «проверка не запускается второй раз параллельно самой себе» автоматически (без отдельных локов), даже если проба длилась дольше своего интервала — единственная плата: интервал в этом случае временно «плывёт» (запуск позже расписания), что задокументировано как сознательный трейд-офф простоты против идеальной пунктуальности.

## 2026-09-15 18:22 (+05:00) — Проблема: жёстко закреплённые версии пакетов не собираются на Python 3.14

При первой установке зависимостей backend (`pip install -r requirements.txt`) с точно
зафиксированными версиями (`pydantic==2.10.4`, `asyncpg==0.30.0` и т.д.) сборка падала и на
Windows, и в WSL2 (Ubuntu 26.04, тоже Python 3.14) — для этих старых версий нет готовых wheel
под cp314, pip уходил в сборку из исходников (`pydantic-core` на Rust), а линковка падала
из-за не до конца настроенного MSVC/Rust тулчейна.

Исправление: в `requirements.txt` заменил точные версии на нижние границы (`>=`), чтобы pip
брал актуальные версии с готовыми wheel под используемый интерпретатор. После этого
`pip install` и `pytest` (health-check) прошли без проблем. Для сдающего проект это тоже
безопаснее: любой более новый/другой Python не упрётся в эту же стену.
