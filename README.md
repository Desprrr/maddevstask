# Монитор доступности сайтов

Тестовое задание "Agentic Developer" — Задание 3. Пользователь добавляет проверки сайтов
(URL, интервал, таймаут, ожидаемый код/строка), сервис регулярно их опрашивает, отслеживает
инциденты, шлёт оповещения на почту и показывает живую панель статусов и публичную страницу
статуса — без перезагрузки страницы, для нескольких одновременно открытых клиентов.

## Стек и почему так

- **Backend: Python + FastAPI (asyncio).** Планировщик проверок — по сути I/O-bound задача
  (сеть, ожидание ответа десятков сайтов параллельно), под это естественно ложится asyncio.
  Starlette (на котором стоит FastAPI) даёт нативный WebSocket без сторонних библиотек.
- **Frontend: Vue 3 + TypeScript + Vite.** Скаффолд создан генератором
  `npm create vite@latest -- --template vue-ts` (шаблон официальный, весь код внутри — свой).
- **СУБД: PostgreSQL** (SQLAlchemy async + asyncpg, миграции Alembic).
- **Почта:** абстракция `EmailSender` с двумя реализациями — `SmtpEmailSender` (реальный SMTP,
  рассчитан на Mailpit в docker-compose) и `FakeEmailSender` (только запись в БД, для локальной
  разработки без почтового сервера). Обе всегда пишут в таблицу `sent_emails` — единый outbox,
  по которому видно, что письмо реально "отправлено", независимо от backend'а.
- **Симулятор проверяемых сайтов:** отдельный сервис `target-emulator` — входит в задание,
  умеет отвечать успехом, нужным/ненужным кодом, медленно, нестабильно или не отвечать вовсе.
- **Учётные записи:** без входа (single-tenant инструмент). Публичная страница — не второй тип
  пользователя, а read-only срез по флагу `is_public` на чеке. Подробное обоснование и все
  остальные решения по ходу разработки — в [`DECISIONS.md`](./DECISIONS.md), с таймштампами от
  самого начала работы до этой строки.

## Структура репозитория

```
backend/            FastAPI backend (app/, alembic/, tests/)
target-emulator/    сервис-эмулятор проверяемых сайтов (входит в задание)
frontend/           Vue 3 + TS фронтенд
docker-compose.yml  postgres + mailpit + backend + target-emulator + frontend
DECISIONS.md        лог решений с таймштампами — как и почему устроено именно так
```

## Запуск

### Вариант 1: Docker (рекомендуется, поднимает всё одной командой)

Требования: Docker + Docker Compose.

```bash
docker compose up --build
```

Поднимутся: PostgreSQL, Mailpit (эмулятор почты), `target-emulator`, backend и frontend.
Backend сам применит миграции и один раз засеет демо-данные (5 проверок на `target-emulator` —
рабочая, медленная-но-живая, с неверным кодом, нестабильная, не отвечающая — сразу видно живую
работу, а не пустой экран).

После запуска:

| Что | Адрес |
|---|---|
| Приложение (дашборд) | http://localhost:8080 |
| Публичная страница статуса | http://localhost:8080/status |
| Backend API напрямую | http://localhost:8000 |
| Почтовый инбокс (Mailpit) | http://localhost:8025 |
| `target-emulator` напрямую | http://localhost:9100 |

Это не гипотетическая инструкция — она реально прогнана на машине без изначально установленного
Docker: он был отдельно поставлен (Docker Engine + compose plugin в WSL2) специально для того,
чтобы проверить `docker compose up` от начала до конца, а не сдать написанным "на веру". По
пути нашлись и были исправлены два реальных препятствия (конфликт порта 5432 с локальным
Postgres и осиротевший контейнер без сети после первой неудачной попытки) — подробности и как
чинилось в [`DECISIONS.md`](./DECISIONS.md) (запись от 16.09, "docker-compose и Dockerfile'ы").

### Вариант 2: вручную (для разработки)

Требования: Python 3.12+, Node.js 20+, PostgreSQL 14+ (запущенный локально или доступный по сети).

**1. База данных.** Создайте БД и роль (имена — на ваш выбор, ниже — то, что ожидает
`.env.example` по умолчанию):

```sql
CREATE ROLE monitor LOGIN PASSWORD 'monitor';
CREATE DATABASE monitor OWNER monitor;
```

**2. target-emulator** (отдельный терминал):

```bash
cd target-emulator
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app:app --port 9100
```

**3. Backend** (отдельный терминал):

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # при необходимости поправьте DATABASE_URL
alembic upgrade head
python -m app.seed     # опционально: демо-данные на target-emulator
uvicorn app.main:app --reload --port 8000
```

По умолчанию `EMAIL_BACKEND=fake` — письма не отправляются по-настоящему, только пишутся в
таблицу `sent_emails` (плюс лог). Чтобы проверить реальную отправку, поднимите Mailpit
(`docker run -d -p 8025:8025 -p 1025:1025 axllent/mailpit`) и поставьте в `.env`
`EMAIL_BACKEND=smtp`, `SMTP_HOST=localhost`, `SMTP_PORT=1025`.

**4. Frontend** (отдельный терминал):

```bash
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173 — dev-сервер Vite проксирует `/api` и `/ws` на `localhost:8000`
(см. `frontend/vite.config.ts`), отдельно настраивать CORS не нужно.

### Тесты

```bash
cd backend
source .venv/bin/activate
pytest -q
```

53 теста: CRUD, планировщик (конкурентность на управляемых фейковых пробах, без реальной сети —
быстро и детерминированно), детекция инцидентов, окна обслуживания и подавление писем, sweep
рассылки писем, WebSocket-рассылка, история/агрегация, публичная страница. Отдельно —
живые ручные проверки через браузер и `target-emulator` (описаны в `DECISIONS.md`) на то, что
не покрыть юнит-тестами: реальный HTTP end-to-end, два одновременно открытых клиента, реальная
доставка писем по SMTP в docker-compose.

## Что работает

- Проверки: создание, пауза/возобновление, ручной запуск, удаление; интервал 30с–1ч, таймаут,
  ожидаемый код, опционально ожидаемая строка в теле.
- Группы проверок с общими адресами оповещений.
- Живая панель статусов: состояние, время ответа, когда проверено, сколько длится падение —
  обновляется по WebSocket без перезагрузки, включая структурные изменения (пауза/удаление/
  создание чека или группы — не только смена статуса).
- Инциденты: порог "кратковременный сбой ≠ падение" (2 подряд неудачи), журнал с длительностью,
  корректная работа при перезапуске сервера (открытый инцидент не теряется и не дублируется).
- Окна обслуживания на уровне чека: проверки идут, письма подавляются, досылаются сразу после
  окончания окна, если падение всё ещё активно.
- Письма (DOWN/RECOVERED) — ровно по одному на переход, с реальной SMTP-доставкой в
  docker-compose (Mailpit) и с fake-outbox для разработки без почтового сервера.
- История и агрегация (сутки/неделя/месяц) с процентом доступности за период.
- Публичная страница статуса без входа — показывает только то, что помечено `is_public`,
  включая группировку и агрегированный статус группы; приватный чек внутри смешанной группы не
  утекает и не портит публичный статус группы.
- Работает при нескольких одновременно открытых клиентах (проверено вручную в двух вкладках —
  и панель статусов, и админские действия, и публичная страница).
- Переживает перезапуск сервера: данные в Postgres, открытые инциденты и настройки не теряются;
  пропуски в данных за время простоя — это пробел в истории, а не засчитанное падение.
- `docker compose up --build` — весь стек одной командой, проверено вживую от начала до конца.

## Что не делали и почему (честно)

- **Нет UI для редактирования уже созданного чека** (изменить URL/интервал и т.п.). Backend это
  умеет (`PATCH /api/checks/{id}`), но в задании для этого сценария явно перечислено только
  "добавить, приостановить, возобновить, удалить, запустить вручную" — редактирование не входит
  в обязательный список, и UI для него не строился, чтобы не раздувать объём сверх нужного.
- **Окна обслуживания на уровне группы** backend поддерживает (`group_id` в
  `POST /api/maintenance-windows`), но отдельного экрана управления групповыми окнами во
  фронтенде нет — только окна конкретного чека со страницы этого чека.
- **Порог инцидента (2 подряд неудачи) — фиксированная константа**, не настраивается по каждому
  чеку отдельно. Осознанный выбор ради объёма (задание оставляет порог на наше усмотрение).
- **Нет реальной авторизации.** Решение "без входа" (см. `DECISIONS.md`, запись от 18:07) — это
  значит, что разделение "публичное/приватное" курирует, что показывает конкретный экран, а не
  является защищённой границей: у API в принципе нет проверки прав ни на один эндпоинт. Это
  прямое следствие выбранной модели доступа, а не недосмотр — но если бы это было нужно закрыть
  по-настоящему, потребовалась бы хотя бы простая авторизация на admin-API.
- **История хранится как сырые строки** (`check_results`) без отдельных таблиц-агрегатов —
  агрегация делается на лету SQL-запросом (`date_trunc` + `GROUP BY`) с индексом
  `(check_id, checked_at)`. Для объёма этого проекта (демо/оценочное задание) этого достаточно
  и просто; при реальной нагрузке в продакшене на очень больших объёмах уже стоило бы задуматься
  о материализованных агрегатах или отдельном хранилище временных рядов.
- **Планировщик — один процесс, in-memory.** `Scheduler`/`ConnectionManager` хранят состояние
  (запущенные задачи, WS-соединения) в памяти одного процесса — приложение рассчитано на один
  backend-контейнер/воркер. Горизонтальное масштабирование потребовало бы вынести это в общее
  хранилище (Redis pub/sub для WS-рассылки между инстансами, распределённый лок или отдельный
  scheduler-процесс для проверок) — вне объёма этого задания.

## Что сделали бы следующим заходом

- UI для редактирования чека и для окон обслуживания на уровне группы (backend уже готов).
- Настраиваемый порог инцидента (сейчас — константа на уровне приложения).
- Простая авторизация для admin-API, если понадобится реальное разделение прав, а не только
  курирование того, что показывает публичная страница.
- Материализованные агрегаты истории (rollup-таблицы или TimescaleDB-подобное решение) для
  большого объёма исторических данных — сейчас агрегация "на лету" вполне достаточна для
  тестового объёма, но не бесконечно масштабируется.
- Горизонтальное масштабирование backend (сейчас — один процесс с состоянием в памяти):
  Redis pub/sub для WS между инстансами, распределённая координация планировщика.
- Больше типов оповещений (Slack/Telegram) поверх уже существующей абстракции `EmailSender` —
  структура (абстрактный отправитель + единый outbox) уже позволяет добавить второй канал, не
  трогая логику принятия решения "когда слать".

## Промпты и работа с AI-агентом

Проект разрабатывался с **Claude Code** (Anthropic), модель **Claude Sonnet 5**. Выбор
инструмента — Claude Code даёт агенту прямой доступ к shell, файловой системе и браузеру в
одной сессии, а не только к чату: для этой задачи это означало реальный запуск `pytest` и
`docker compose up`, живую проверку в браузере (в том числе с двумя одновременно открытыми
вкладками) и установку недостающих инструментов (PostgreSQL, затем и сам Docker — через WSL2)
по ходу дела, а не только генерацию кода "на веру". Модель — Sonnet 5 как баланс между
качеством инженерных решений (конкурентность планировщика, корректность инцидент-логики) и
скоростью на задаче такого объёма.

Полный лог решений, найденных проблем и их исправлений — с таймштампами от самого первого
шага (выбор сценария) до последнего — в [`DECISIONS.md`](./DECISIONS.md). Он и есть журнал
разработки, замена промпт-экспорта: там видно не только "что сделано", но и "почему именно
так", включая моменты, где первый вариант оказывался неверным и переделывался.
