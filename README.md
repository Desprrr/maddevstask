# Монитор доступности сайтов

Тестовое задание "Agentic Developer" — Задание 3. Пользователь добавляет проверки сайтов
(URL, интервал, таймаут, ожидаемый код/строка), сервис регулярно их опрашивает, отслеживает
инциденты, шлёт оповещения на почту и показывает живую панель статусов и публичную страницу
статуса — без перезагрузки страницы, для нескольких одновременно открытых клиентов.

[![CI](https://github.com/Desprrr/maddevstask/actions/workflows/ci.yml/badge.svg)](https://github.com/Desprrr/maddevstask/actions/workflows/ci.yml)

## Стек и почему так

- **Backend: Python + FastAPI (asyncio).** Планировщик проверок — по сути I/O-bound задача
  (сеть, ожидание ответа десятков сайтов параллельно), под это естественно ложится asyncio.
  Starlette (на котором стоит FastAPI) даёт нативный WebSocket без сторонних библиотек.
- **Frontend: Vue 3 + TypeScript + Vite.** Скаффолд создан генератором
  `npm create vite@latest -- --template vue-ts` (шаблон официальный, весь код внутри — свой).
- **СУБД: PostgreSQL** (SQLAlchemy async + asyncpg, миграции Alembic).
- **Почта:** абстракция `EmailSender` с двумя реализациями — `SmtpEmailSender` (реальный SMTP,
  рассчитан на Mailpit в docker-compose) и `FakeEmailSender` (только запись в БД, для локальной
  разработки без почтового сервера). Обе всегда пишут в таблицу `sent_emails` — единый outbox,
  по которому видно, что письмо реально "отправлено", независимо от backend'а.
- **Симулятор проверяемых сайтов:** отдельный сервис `target-emulator` — входит в задание,
  умеет отвечать успехом, нужным/ненужным кодом, медленно, нестабильно или не отвечать вовсе.
- **Учётные записи:** без входа (single-tenant инструмент). Публичная страница — не второй тип
  пользователя, а read-only срез по флагу `is_public` на чеке. Подробное обоснование и все
  остальные решения по ходу разработки — в [`DECISIONS.md`](./DECISIONS.md), с таймштампами от
  самого начала работы до этой строки.

## Архитектура

### Поток данных: от пробы до письма и живого обновления

```
Scheduler (один asyncio.Task на активный чек)
   │  next run = момент завершения предыдущего + interval_seconds
   │  (никогда не запускает пробу параллельно самой себе)
   ▼
prober.probe(check)  ── общий httpx.AsyncClient на процесс ──▶ проверяемый сайт
   │
   ▼
CheckResult записан в БД
   │
   ├──▶ ConnectionManager.broadcast_check_result()  ──▶ /ws/admin (всегда)
   │                                                 └─▶ /ws/public (если check.is_public)
   │
   ▼
incidents.evaluate(check, result)   — 2 подряд неудачи открывают инцидент, первый успех закрывает;
   │                                   решение всегда берётся из БД, не из памяти (restart-safe)
   ▼
IncidentEvent (opened/closed) ──▶ ConnectionManager.broadcast_incident_event() ──▶ /ws/admin, /ws/public
                                                        │
                                                        ▼
                                    AlertDispatcher (отдельный цикл, раз в 20с)
                                    сканирует несквитанные инциденты, проверяет окна
                                    обслуживания, шлёт письмо через EmailSender
```

CRUD-действия (создать/удалить/поставить на паузу чек или группу, окно обслуживания) идут
отдельным путём: после мутации в БД рассылается лёгкий сигнал
`ConnectionManager.broadcast_admin_changed()` (`{"type": "admin.changed"}`) на `/ws/admin` — фронтенд в ответ
просто перезапрашивает списки, поэтому все открытые вкладки админки видят одно и то же не
только по статусам, но и по составу чеков/групп.

### Backend (`backend/app/`)

| Модуль | Отвечает за |
|---|---|
| `models/` | SQLAlchemy ORM: `Group`, `GroupAlertEmail`, `Check`, `CheckResult`, `Incident`, `MaintenanceWindow`, `SentEmail` |
| `schemas/` | Pydantic-модели запросов/ответов API |
| `api/checks.py` | CRUD чеков, pause/resume/run-now, `/status` (панель), `/history` (агрегация), `/incidents` (журнал) |
| `api/groups.py` | CRUD групп и их адресов оповещений |
| `api/maintenance_windows.py` | CRUD окон обслуживания |
| `api/public.py` | `GET /public/status` — курированный снапшот для публичной страницы |
| `api/ws.py` | WebSocket-эндпоинты `/ws/admin`, `/ws/public` |
| `scheduler/engine.py` | `Scheduler` — по одной asyncio-задаче на активный чек, `run-now`, гарантия отсутствия параллельного запуска самого себя |
| `scheduler/prober.py` | Одна HTTP-проба; общий `httpx.AsyncClient` на процесс (пул соединений — важно под нагрузку многих чеков) |
| `incidents.py` | Открытие/закрытие инцидентов по порогу подряд-неудач; вся история берётся из БД, ничего не хранит в памяти |
| `alerting/email_sender.py` | Абстракция `EmailSender`: `FakeEmailSender` (только outbox в БД) / `SmtpEmailSender` (реальный SMTP) |
| `alerting/dispatcher.py` | Периодический sweep: кому ещё не отправлено письмо, не идёт ли сейчас окно обслуживания |
| `realtime/connection_manager.py` | Пулы WS-подключений admin/public, рассылка событий |
| `db.py`, `config.py` | Async engine/session factory, настройки из окружения |
| `seed.py` | Идемпотентные демо-данные на `target-emulator` |
| `alembic/` | Миграции схемы БД |

### Frontend (`frontend/src/`)

| Модуль | Отвечает за |
|---|---|
| `api/http.ts` | Типизированный REST-клиент (относительные пути `/api/...`) |
| `api/ws.ts` | WebSocket-клиент с автопереподключением (экспоненциальный backoff); после каждого (пере)подключения подписчик перезапрашивает снимок — события за время обрыва не теряются |
| `stores/checks.ts`, `stores/groups.ts` | Pinia: состояние админки + применение live-событий с сервера |
| `stores/publicStatus.ts` | Состояние публичной страницы: снимок, live-события, `public.changed` |
| `views/DashboardView.vue` | Админка: CRUD групп/чеков, живая панель статусов |
| `views/CheckDetailView.vue` | График истории (ось времени, простои мониторинга затенены), журнал инцидентов, окна обслуживания чека и его группы |
| `views/GroupDetailView.vue` | Страница группы: её проверки и окна обслуживания на всю группу |
| `views/PublicStatusView.vue` | Публичная страница статуса (без входа) |
| `components/MaintenanceWindows.vue` | Список/создание/удаление окон обслуживания — для чека или группы |
| `utils/historyChart.ts` | Точки графика истории: разрывы линии и затенение простоев мониторинга |
| `composables/useNow.ts` | Тикающие "часы" для живого отображения длительности падения |

### Хранилище

7 таблиц (см. `backend/alembic/versions/` для точной схемы): `groups` + `group_alert_emails`
(группы и адреса оповещений), `checks` (сами проверки), `check_results` (сырая история проб,
индекс `(check_id, checked_at)` под быструю агрегацию), `incidents` (журнал падений),
`maintenance_windows` (окна обслуживания на чек или группу), `sent_emails` (outbox — доказательство
отправки писем независимо от backend'а).

## Запуск

### Вариант 1: Docker (рекомендуется, поднимает всё одной командой)

Требования: Docker + Docker Compose.

```bash
docker compose up --build
```

Поднимутся: PostgreSQL, Mailpit (эмулятор почты), `target-emulator`, backend и frontend.
Backend сам применит миграции и один раз засеет демо-данные (5 проверок на `target-emulator` —
рабочая, медленная-но-живая, с неверным кодом, нестабильная, не отвечающая — сразу видно живую
работу, а не пустой экран).

После запуска (порты — дефолтные, см. ниже, если заняты):

| Что | Адрес |
|---|---|
| Приложение (дашборд) | http://localhost:8080 |
| Публичная страница статуса | http://localhost:8080/status |
| Backend API напрямую | http://localhost:8000 |
| Почтовый инбокс (Mailpit) | http://localhost:8025 |
| `target-emulator` напрямую | http://localhost:9100 |

**Если порт занят.** На сервере (а не только на чистой локальной машине) порт 8000 — один из
самых часто занятых кем-то другим. Все хостовые порты настраиваются переменными окружения без
правки `docker-compose.yml` — либо скопируйте `.env.example` в `.env` и поправьте нужные, либо
задайте прямо при запуске:

```bash
BACKEND_PORT=8001 FRONTEND_PORT=8081 docker compose up --build
```

Postgres и SMTP-порт Mailpit (1025) на хост вообще не публикуются — они нужны только внутри
docker-сети, конфликтовать с чем-то на хосте им нечем в принципе.

Это не гипотетическая инструкция — она реально прогнана на машине без изначально установленного
Docker: он был отдельно поставлен (Docker Engine + compose plugin в WSL2) специально для того,
чтобы проверить `docker compose up` от начала до конца, а не сдать написанным "на веру". По
пути нашлись и были исправлены реальные препятствия (конфликт порта 5432 с локальным Postgres,
осиротевший контейнер без сети после первой неудачной попытки, а позже — конфликт порта 8000
backend'а с чем-то посторонним на реальном сервере пользователя, воспроизведённый и закрытый
через настраиваемые порты выше) — подробности и как чинилось в [`DECISIONS.md`](./DECISIONS.md)
(записи от 16.09, "docker-compose и Dockerfile'ы" и "порт 8000 занят на сервере").

### Вариант 2: вручную (для разработки)

Требования: Python 3.12+, Node.js 20+, PostgreSQL 14+ (запущенный локально или доступный по сети).

**1. База данных.** Создайте БД и роль (имена — на ваш выбор, ниже — то, что ожидает
`.env.example` по умолчанию):

```sql
CREATE ROLE monitor LOGIN PASSWORD 'monitor';
CREATE DATABASE monitor OWNER monitor;
```

**2. target-emulator** (отдельный терминал):

```bash
cd target-emulator
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
uvicorn app:app --port 9100
```

**3. Backend** (отдельный терминал):

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env   # при необходимости поправьте DATABASE_URL
alembic upgrade head
python -m app.seed     # опционально: демо-данные на target-emulator
uvicorn app.main:app --reload --port 8000
```

По умолчанию `EMAIL_BACKEND=fake` — письма не отправляются по-настоящему, только пишутся в
таблицу `sent_emails` (плюс лог). Чтобы проверить реальную отправку, поднимите Mailpit
(`docker run -d -p 8025:8025 -p 1025:1025 axllent/mailpit`) и поставьте в `.env`
`EMAIL_BACKEND=smtp`, `SMTP_HOST=localhost`, `SMTP_PORT=1025`.

**4. Frontend** (отдельный терминал):

```bash
cd frontend
npm install
npm run dev
```

Откройте http://localhost:5173 — dev-сервер Vite проксирует `/api` и `/ws` на `localhost:8000`
(см. `frontend/vite.config.ts`), отдельно настраивать CORS не нужно.

### Тесты

```bash
cd backend
source .venv/bin/activate
pytest -q
```

81 тест backend: CRUD, планировщик (конкурентность на управляемых фейковых пробах, без реальной
сети — быстро и детерминированно), детекция инцидентов, простой монитора и пауза, окна
обслуживания и подавление писем, sweep рассылки писем, WebSocket-рассылка (включая урезанный
публичный канал), история/агрегация и разрывы, публичная страница, масштабирование запросов
статуса по объёму истории (через `EXPLAIN ANALYZE`, без замеров времени).

```bash
cd frontend
npm test
```

16 тестов frontend (Vitest + happy-dom): переподключение WS и перезапрос снимка, публичная
страница (`public.changed`, пауза не роняет группу), построение графика с разрывами, компонент
окон обслуживания. Отдельно —
живые ручные проверки через браузер и `target-emulator` (описаны в `DECISIONS.md`) на то, что
не покрыть юнит-тестами: реальный HTTP end-to-end, два одновременно открытых клиента, реальная
доставка писем по SMTP в docker-compose.

## Деплой на свой сервер

Минимальный вариант — тот же `docker-compose.yml`, что и для локального запуска, на любом
сервере с Docker (VPS, облачная VM и т.п.). Собственно приложение не завязано на localhost —
все внутренние обращения идут по именам docker-сервисов (`postgres`, `backend`,
`target-emulator`), поэтому специфичного для локальной машины в стеке нет. Для реального
сервера стоит поменять несколько вещей:

1. **Секреты и пароли.** `POSTGRES_PASSWORD`/`DATABASE_URL` в `docker-compose.yml` сейчас —
   `monitor`/`monitor`, это годится только для локальной разработки. Смените на сгенерированный
   пароль (и не коммитьте его — вынесите в `.env`, который `docker-compose.yml` может читать
   через `env_file:`, или в секреты CI/хостинга).
2. **Почта.** Mailpit — заглушка, письма из неё никуда за пределы сервера не уходят. Для
   реальной отправки замените `SMTP_HOST`/`SMTP_PORT`/`SMTP_FROM` у сервиса `backend` на
   настоящий SMTP-relay (например, стороннего провайдера транзакционной почты) — `EMAIL_BACKEND`
   уже `smtp`, менять код не придётся, только переменные окружения.
3. **CORS и адрес фронтенда.** `CORS_ORIGINS` у backend сейчас `["http://localhost:8080"]` —
   поменяйте на реальный домен. Если фронтенд и backend будут на одном домене через nginx
   (как в `frontend/nginx.conf`), CORS вообще не понадобится — оставьте как есть или сузьте.
4. **Реверс-прокси и TLS.** Порт `FRONTEND_PORT` (по умолчанию 8080, frontend/nginx) —
   единственное, что имеет смысл выставлять наружу напрямую. Поставьте перед ним
   nginx/Caddy/Traefik с настоящим сертификатом (Let's Encrypt) и проксируйте на
   `127.0.0.1:$FRONTEND_PORT` контейнера. Postgres и SMTP-порт Mailpit на хост уже не
   публикуются вовсе (см. "Если порт занят" выше) — их не нужно отдельно закрывать. Backend
   (`BACKEND_PORT`, по умолчанию 8000) публикуется ради прямого curl/отладки — на реальном
   сервере либо уберите его строку `ports:` совсем (frontend всё равно достаёт backend по
   внутренней docker-сети, а не через этот порт), либо ограничьте доступ к нему на уровне
   файрвола/security group, не оставляя открытым для всего интернета.
5. **Бэкапы.** Все данные — в именованном volume `pgdata`. Регулярный `pg_dump` из контейнера
   `postgres` (`docker compose exec postgres pg_dump -U monitor monitor > backup.sql`) — самый
   простой вариант для объёма этого проекта.

Дальше — то же самое, что и локально:

```bash
git clone https://github.com/Desprrr/maddevstask.git
cd maddevstask
# поправить пароли/SMTP/CORS в docker-compose.yml или через .env, см. пункты выше
docker compose up --build -d
```

## Что работает

- Проверки: создание, пауза/возобновление, ручной запуск, удаление; интервал 30с–1ч, таймаут,
  ожидаемый код, опционально ожидаемая строка в теле.
- Группы проверок с общими адресами оповещений.
- Живая панель статусов: состояние, время ответа, когда проверено, сколько длится падение —
  обновляется по WebSocket без перезагрузки, включая структурные изменения (пауза/удаление/
  создание чека или группы — не только смена статуса).
- Инциденты: порог "кратковременный сбой ≠ падение" (2 подряд неудачи без разрыва между ними),
  журнал с длительностью и тем, чем инцидент закончился (сайт восстановился / мониторинг
  прерывался / проверку поставили на паузу).
- Окна обслуживания на уровне чека и на уровне группы (отдельная страница группы): проверки идут,
  письма подавляются. Падение, целиком уложившееся в окно, писем не порождает вовсе; если
  падение продолжается после окна — DOWN уходит сразу после его окончания.
- Письма (DOWN/RECOVERED) — ровно по одному на переход, с реальной SMTP-доставкой в
  docker-compose (Mailpit) и с fake-outbox для разработки без почтового сервера.
- История и агрегация (сутки/неделя/месяц) с процентом доступности за период. График по оси
  времени; интервалы, когда мониторинг не работал, затенены и в доступность не входят.
- Публичная страница статуса без входа — показывает только то, что помечено `is_public`,
  включая группировку и агрегированный статус группы; приватный чек внутри смешанной группы не
  утекает и не портит публичный статус группы.
- Работает при нескольких одновременно открытых клиентах (проверено вручную в двух вкладках —
  и панель статусов, и админские действия, и публичная страница).
- Переживает перезапуск сервера: данные в Postgres, настройки не теряются. Простой монитора — не
  простой сайта: неудачи до и после простоя не складываются в одну серию, открытый инцидент
  закрывается на последнем результате перед простоем, а не растягивается на время простоя;
  повторного DOWN после рестарта посреди падения нет. Клиенты после переподключения WS
  перезапрашивают снимок, так что статус не залипает.
- Публичный WebSocket-канал отдаёт не больше публичного REST (без текстов ошибок, кодов ответа,
  времени ответа) и сообщает публичной странице об изменении состава (`public.changed`).
- `docker compose up --build` — весь стек одной командой, проверено вживую от начала до конца.
- 50 одновременных проверок не мешают друг другу и не тормозят интерфейс (нагрузочный скрипт,
  не только архитектурный расчёт — см. `DECISIONS.md`); история за месяц (86400 строк на один
  чек) агрегируется на лету за ~0.25с end-to-end. Панель статусов и публичная страница берут
  последний результат через `LATERAL ... LIMIT 1` — их скорость не зависит от объёма истории
  (4,32 млн строк: ~0,6мс на запрос).
- CI (`.github/workflows/ci.yml`): тесты backend, target-emulator и frontend (Vitest), сборка frontend, полная
  сборка и e2e-прогон `docker compose` на каждый push/PR в `main`.

## Что не делали и почему (честно)

- **Нет UI для редактирования уже созданного чека** (изменить URL/интервал и т.п.). Backend это
  умеет (`PATCH /api/checks/{id}`), но в задании для этого сценария явно перечислено только
  "добавить, приостановить, возобновить, удалить, запустить вручную" — редактирование не входит
  в обязательный список, и UI для него не строился, чтобы не раздувать объём сверх нужного.
- **Нет ретеншена истории.** `check_results` растёт бесконечно (50 проверок с интервалом 30с —
  ~4,3 млн строк в месяц). На скорость панели статусов это не влияет (см. выше), на объём диска
  и агрегацию за месяц — влияет.
- **Порог разрыва мониторинга берётся из текущего интервала проверки.** Если интервал поменяли,
  старые разрывы на графике и в логике инцидентов оцениваются по новому интервалу.
- **Порог инцидента (2 подряд неудачи) — фиксированная константа**, не настраивается по каждому
  чеку отдельно. Осознанный выбор ради объёма (задание оставляет порог на наше усмотрение).
- **Нет реальной авторизации.** Решение "без входа" (см. `DECISIONS.md`, запись от 18:07) — это
  значит, что разделение "публичное/приватное" курирует, что показывает конкретный экран, а не
  является защищённой границей: у API в принципе нет проверки прав ни на один эндпоинт. Это
  прямое следствие выбранной модели доступа, а не недосмотр — но если бы это было нужно закрыть
  по-настоящему, потребовалась бы хотя бы простая авторизация на admin-API.
- **История хранится как сырые строки** (`check_results`) без отдельных таблиц-агрегатов —
  агрегация делается на лету SQL-запросом (`date_trunc` + `GROUP BY`) с индексом
  `(check_id, checked_at)`. Для объёма этого проекта (демо/оценочное задание) этого достаточно
  и просто; при реальной нагрузке в продакшене на очень больших объёмах уже стоило бы задуматься
  о материализованных агрегатах или отдельном хранилище временных рядов.
- **Планировщик — один процесс, in-memory.** `Scheduler`/`ConnectionManager` хранят состояние
  (запущенные задачи, WS-соединения) в памяти одного процесса — приложение рассчитано на один
  backend-контейнер/воркер. Горизонтальное масштабирование потребовало бы вынести это в общее
  хранилище (Redis pub/sub для WS-рассылки между инстансами, распределённый лок или отдельный
  scheduler-процесс для проверок) — вне объёма этого задания.
- **Монетизация / платный доступ не проектировались.** Если бы сервис делился на бесплатных и
  платных пользователей, потребовалась бы генерация ключа доступа при успешной транзакции и
  выдача его пользователю после оплаты — с активацией более широких возможностей (например,
  более короткий минимальный интервал проверки, больше проверок на аккаунт, приоритетные
  оповещения). Сознательно не проектировали и не решали внедрять — платёжный/лицензионный слой
  за рамками тестового задания, проект — MVP с одним общим тарифом возможностей.

## Что сделали бы следующим заходом

- UI для редактирования чека (backend уже готов).
- Ретеншен сырой истории (например, хранить сырые пробы 30–90 дней, дальше — только агрегаты).
- Настраиваемый порог инцидента (сейчас — константа на уровне приложения).
- Простая авторизация для admin-API, если понадобится реальное разделение прав, а не только
  курирование того, что показывает публичная страница.
- Материализованные агрегаты истории (rollup-таблицы или TimescaleDB-подобное решение) для
  большого объёма исторических данных — сейчас агрегация "на лету" вполне достаточна для
  тестового объёма, но не бесконечно масштабируется.
- Горизонтальное масштабирование backend (сейчас — один процесс с состоянием в памяти):
  Redis pub/sub для WS между инстансами, распределённая координация планировщика.
- Больше типов оповещений (Slack/Telegram) поверх уже существующей абстракции `EmailSender` —
  структура (абстрактный отправитель + единый outbox) уже позволяет добавить второй канал, не
  трогая логику принятия решения "когда слать".
